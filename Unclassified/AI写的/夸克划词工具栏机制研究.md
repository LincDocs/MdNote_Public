## 0. 一句话结论

> 它**没有**去定位"选中的文本在哪里"，也**没有**用 TSF。
> 它做的是：**全局监听鼠标"按下→拖动→抬起"这个动作** + **用进程名白名单判断该不该管** + **用 MSAA（不是 UIA）或模拟复制去取选中文本** + **把鼠标坐标当成工具栏位置**。
> 你的新猜测（"只是检测鼠标框选动作 + 查窗口是不是在白名单里"）基本正确，只差两点修正：
> 1）判定的粒度是**进程名**（`Code.exe` / `NOTEPAD.EXE` …），不是窗口标题；
> 2）取文本是**两级策略**（MSAA 优先 → 模拟 Ctrl+Insert 兜底，且剪贴板会完整恢复）。

个人补充：这里的模拟 `Ctrl+Insert` 在夸克的实际使用中会有bug，经常导致 `Insert` 状态无法正常恢复

## 2. 触发层：它到底"检测"了什么

### 2.1 从字符串直接读出来的流水线

`quark.dll` 里同一批日志字符串（`.rdata` 按编译单元连续排列，地址 0x0110945xx–0x0110954xx）几乎等于伪代码：

```
LauncherWindows::OnMouseLButtonDownEvent   skip key_downing
LauncherWindows::OnMouseLButtonDownEvent   skip current_wnd null
LauncherWindows::OnMouseLButtonDownEvent   accepted process=
LauncherWindows::StartLauncher              skip background_wnd null
LauncherWindows::StartLauncher              trigger start
LauncherWindows::ShowSelectionWindowIfNeeded skip not processing
LauncherWindows::ShowSelectionWindowIfNeeded show selection process=..., text_length=
LauncherWindows::ShowSelectionWindowIfNeeded no selection
LauncherWindows::RegisterShortcut           shortcut_id=..., accelerator=
```

翻译一下：

1. **鼠标左键按下**时先做一道廉价过滤：
   - `key_downing`：当前是否有键按住（`GetAsyncKeyState`）→ 有（比如 Shift/Ctrl）就跳过；
   - `current_wnd null`：光标下没有窗口 → 跳过；
   - `accepted process=`：**取光标下窗口所属进程名，命中白名单才继续**。
2. 通过后 `StartLauncher`（需要 `background_wnd` 存在，说明它是常驻的，不是每次新建）。
3. 抬键后 `ShowSelectionWindowIfNeeded`：**先把选中文本取出来**（日志里紧接着 `text_length=`），
   取到非空才弹；取不到就 `no selection` 什么都不弹。

### 2.2 位置：确实不查选区，只查鼠标

你的观察完全正确，代码也印证：

- 没有任何"求选区矩形"的迹象（既没 `UIA_TextPatternId::GetSelection`，也没做 Chromium AX 的 bounding box 回传）；
- 位置参数来自弹窗组件本身：字符串里有 `auto_size_to_screen`、`auto_size_to_screen_bottom_space`、
  `horizontal_align`、`vertical_align`、`popup_inside_view_radius`、`draggable_top/bottom`、
  `popup_close_on_deactivate(_delay)`
  → 即"以鼠标点为锚，上方放不下就按 `auto_size_to_screen_bottom_space` 翻到下方"，而不是"贴着选区"。

所以你看到"选中框不动、工具栏上下偏移"是**设计如此**，不是 bug。

### 2.3 用了哪个 Win32 原语？

`quark.dll` 的导入表被做了手脚（可见 Import Directory 只有 15 个 DLL），但 **Delay-Load 目录是完整的**，
我把它解出来（`0x127d63d0`，48 个 DLL），里面一次性出现了所有"全局监听"的可能选项：

```
USER32.dll (delay-import 节选)
  SetWindowsHookExW, CallNextHookEx, UnhookWindowsHookEx      ← 低层鼠标/键盘钩子
  RegisterRawInputDevices, GetRawInputData, DefRawInputProc    ← Raw Input（RIDEV_INPUTSINK 可后台收）
  SetWinEventHook, UnhookWinEvent                              ← WinEvent 全局事件
  GetLastInputInfo, GetMessageTime, GetMessagePos, GetCursorInfo,
  GetCursorPos, GetGUIThreadInfo, GetAsyncKeyState, GetKeyState,
  TrackMouseEvent, GetDoubleClickTime
  OpenClipboard/GetClipboardData/SetClipboardData/EmptyClipboard,
  GetClipboardSequenceNumber, IsClipboardFormatAvailable
  SendInput
  WindowFromPoint, GetForegroundWindow, GetClassNameW, EnumWindows, ...
ole32.dll : OleGetClipboard, OleDuplicateData, ReleaseStgMedium   ← 剪贴板"全格式"备份/恢复
OLEACC.dll: AccessibleObjectFromWindow, AccessibleChildren, ...   ← ★ MSAA 客户端（取别的进程的选中文本）
UIAutomationCore.DLL: **只有 Uia*Provider* / UiaReturnRawElementProvider**  ← 只做 provider，不当 UIA 客户端
```

两条重要排除：

- ❌ **不是 TSF**：整套 import 里没有任何 `msctf.h` 侧的东西（`MSCTF.dll` 只是 Chromium/输入法通用加载）。
- ❌ **不是 UIA 客户端取文本**：`UIAutomationCore` 的导入全是 provider 端导出（夸克自己是 Chromium，
  需要向别人提供 UIA 树）。取别家的选中文本走的是 **MSAA（oleacc）**：`AccessibleObjectFromWindow`。

✅ 触发层是"Win32 全局鼠标事件"，但**具体是哪一种我无法从静态证据 100% 断言**（见 §2.4）。
无论哪种，行为等价：它拿到的只是 "按下/抬起 + 屏幕坐标 + 当时的窗口/进程"。

### 2.4 为什么"鼠标时间"这个细节很重要（我的推断）

关键串：

```
SelectionText::GetSelectionTextByClipboard abort mouse time changed before store
SelectionText::GetSelectionTextByClipboard abort mouse time changed after delay
SelectionText::GetSelectionTextByClipboard abort mouse time changed before send ctrl+insert
SelectionText::GetSelectionTextByClipboard abort mouse time changed after ctrl+insert
SelectionText::GetSelectionTextByClipboard abort mouse time changed before return
```

它在剪贴板操作的**每一个异步边界**都重新校验一次"鼠标时间有没有变"。这说明：
它保存了一个"这次交互的时间戳"，一旦用户在取词过程中又动了鼠标/点了别的地方，整条链路立刻放弃
（否则会把别人后来选的东西当成你的选中文本，或者把工具栏弹到错误的地方）。

这种"鼠标事件自带时间戳 + 全程可比对"的写法，最自然的是 **`WH_MOUSE_LL` 钩子**（`MSLLHOOKSTRUCT.time`），
其次才是**定时轮询**（`GetAsyncKeyState(VK_LBUTTON)` + `GetCursorPos` + `GetLastInputInfo`）。
`OnMouseLButtonDownEvent` 这种命名、以及在**按下**时就用 `accepted process=` 做过滤，更像钩子回调。
—— 这一条标记为**推断**，未拿到指令级证据（`quark.dll` 无符号、字符串里也没有钩子安装日志）。

想彻底钉死，可以跑 §7 的实验脚本，或做一次行为实验，见 §7.3。

## 3. 取文本：三级策略（这是最值得抄的部分）

`SelectionText::` 前缀的日志串把实现摊开了：

```
SelectionText::GetText use automation success
SelectionText::GetText use automation empty
SelectionText::GetText skip clipboard by copy blacklist
SelectionText::GetText fallback clipboard
```

### 第 1 级：MSAA（通用）
`AccessibleObjectFromWindow` → `IAccessible` → `get_accSelection` / `IAccessibleText`，
拿不到再退回 `OBJID_CARET`。这条路对 记事本 / Word / 标准编辑框 / Chromium 系（浏览器、VSCode）都有效。
（这解释了你的疑问：**为什么不开 VSCode 无障碍，夸克也能取到** —— Chromium 检测到无障碍客户端访问时会
"按需开启"（on-demand accessibility）AX 树，所以客户端一探就有；见 §6。）

### 第 2 级：COM（表格类）
`quark_app_shared.dll` 里：

```
Excel.Application / KET.Application / KWPS.Application / Word.Application
find selection connection point failed
advise excel selection change failed
selection monitor started / stopped / not running
selected_text / selected_cells
only Excel.Application and KET.Application are supported
```

即对 Excel/WPS 表格用 **COM connection point（Advise）** 监听选区变化，直接读 `Selection`，
因为表格里"复制出来的是单元格文本"，MSAA 给的往往不可用。

### 第 3 级：模拟复制 + 剪贴板（兜底）
关键串（按顺序）：

```
SelectionText::GetSelectionTextByClipboard skip ctrl down
SelectionText::GetSelectionTextByClipboard acquire clipboard mutex failed   ← ScopedNamedMutex
SelectionText::GetSelectionTextByClipboard store_old_clipboard=
SelectionText::GetSelectionTextByClipboard skip store_old_clipboard for process=
SelectionText::GetTextByClipboard ... text_length=
SelectionText::GetSelectionTextByClipboard restore_old_clipboard=
SelectionText::GetSelectionTextByClipboard result=
SelectionText::StoreClipboard OleGetClipboard failed, sc=
SelectionText::StoreClipboard EnumFormatEtc failed, sc=
SelectionText::StoreClipboard get format data failed, format=
SelectionText::StoreClipboard saved format_count=
SelectionText::LockClipboard failed, max_try=
SelectionText::RestoreClipboardContent restored success, success_count=..., failed_count=
SelectionText::SendControlInsert skip ctrl already down
SelectionText::SendCopyShortcut SendInput failed, shortcut=
ctrl + insert
SelectionText::SendControlInsert clipboard sequence unchanged
```

逐条解读 → 这就是一份"生产级实现清单"：

1. **按住 Ctrl 就不做**（否则我们合成的 Ctrl+Insert 会跟用户手上的 Ctrl 打架）。
2. **命名互斥量**串行化（多实例/多线程不能同时动剪贴板）。
3. **全格式备份**：`OleGetClipboard()` 拿 `IDataObject` → `EnumFormatEtc` 枚举**所有**格式 →
   对每个 format `GetData` 一份（`OleDuplicateData`），不是只备份纯文本。
   - `skip store_old_clipboard for process=`：如果剪贴板当前所有者是"某些进程"，干脆不备份
     （典型场景：截图工具正在写图、剪贴板管理器在忙 → 备份会损坏它的数据）。
4. **发 `Ctrl+Insert`，不是 `Ctrl+C`**。（`ctrl + insert` 字符串 + `SendControlInsert` 函数名）
5. **用 `GetClipboardSequenceNumber()` 校验**是否真的变了（`clipboard sequence unchanged` = 复制失败）。
6. 读 `CF_UNICODETEXT`（`OpenClipboard`/`GetClipboardData`/`GlobalLock`，带 `max_try` 重试）。
7. **恢复全部格式**（`RestoreClipboardContent` + `success_count/failed_count`）。
8. 每一步前后做 §2.4 的"鼠标时间"校验，过期即放弃（并且**先恢复剪贴板再返回**）。

**为什么要 Ctrl+Insert？** 这是本次研究里最有实用价值的发现之一，它直接解释了你测试矩阵里的怪现象：

| 应用 | 白名单 | MSAA | Ctrl+Insert 是否等于"复制" | 观察结果 |
|---|---|---|---|---|
| 记事本/Word | ✅ | ✅ | ✅（标准编辑控件） | 生效 |
| 浏览器网页 | ✅(msedge/chrome/firefox) | ✅(Chromium 按需 AX) | ✅（Chromium 绑定 kCopy） | 生效 |
| VSCode | ✅ `Code.exe` | ✅ | ✅（VSCode 默认键位里 `Ctrl+Insert` = copy） | 生效 |
| QQ/微信 | ✅ | ✅（自绘但有 MSAA） | — | 生效 |
| **Typora** | ✅ `Typora.exe` **在白名单里** | ✗ | ✗（CodeMirror 没绑 Ctrl+Insert） | **失败** |
| **Obsidian** | ✗ `Obsidian.exe` 不在名单里 | — | — | 失败 |
| **DSH / 其他 Electron** | ✗ | — | — | 失败 |
| **资源管理器地址栏** | ✗ `explorer.exe` 不在名单里 | — | — | 失败 |

两条结论：
- **Obsidian 失败是"白名单"问题**；**Typora 失败是"取文本"问题**（白名单过了，但 MSAA 空 + Ctrl+Insert 无人响应 → `clipboard sequence unchanged` / `clipboard text empty` → 不弹）。
- 白名单 ≠ 一定能弹；它只是**必要条件**。

另外有 `mintty.exe` 这个硬编码特例（Git Bash 终端），以及 `ai_launcher_wording_copy_blacklist`
（"禁止对它模拟复制"的进程名单，当前服务端值为空）。

字符串里有 `https://www.myquark.cn/?...&qk_module=/browser/ai_launcher&...`）。

### 5.1 运行时实测到的窗口（未触发，静息状态）

```

cls=Chrome_WidgetWin_1  vis=True   rect=(2566,1254, 48, 48)  ex=0x00200088
cls=Chrome_WidgetWin_1  vis=False  rect=(2586,1254,148, 48)  ex=0x00200088
cls=Chrome_WidgetWin_1  vis=False  rect=(2566,1078,168,212)  ex=0x00200088
cls=Chrome_WidgetWin_1  vis=True   rect=(2566,1167, 48, 97)  ex=0x00200088
```

`(333 × 36)` 那个尺寸与"一条 6 个小图标的胶囊"高度吻合，`ex=0x08200088` 拆开是：

- `0x00000080` `WS_EX_TOOLWINDOW` —— 不进任务栏 / 不参与 Alt-Tab
- `0x08000000` `WS_EX_NOACTIVATE` —— **点了不激活、不抢焦点**
- `0x00200000` `WS_EX_NOREDIRECTIONBITMAP` —— 无重定向表面（配合 DirectComposition 合成，Chromium 常用）

推断（标 □ 表示未 100% 证实）：这个窗口就是划词条，**预创建、复用、隐藏着等**，
所以第一次弹出也几乎无延迟；`WS_EX_NOACTIVATE` 是它的灵魂——
如果点击工具条会激活我们自己的窗口，源应用失焦 → 选区消失 → 后面的"复制/翻译"就全废了。
（同理，"先取文本，再弹条"的顺序也避免了这个坑：日志里 `show selection process=..., text_length=`。）

## 6. 回到你的三个痛点 + 我建议的做法

### 痛点 A：「基本拿不到选中文本框的位置」
👉 **别拿了。** 夸克也没拿。位置 = 鼠标坐标；再做一个"上方放不下就翻下 / 出屏就夹到工作区"的自适应。
只保留两个必要修正：**多显示器**（用 `MonitorFromPoint` 取 work area，别用 `GetSystemMetrics`）和
**Per-Monitor DPI**（`GetDpiForWindow`/`WM_DPICHANGED`）。

### 痛点 B：「模拟复制污染剪贴板，还没做恢复」
👉 照 §3 第 3 级做，顺序别改：
`named mutex → OleGetClipboard → EnumFormatEtc 全格式备份 → SendInput(Ctrl+Insert) →
GetClipboardSequenceNumber 校验 → 读 CF_UNICODETEXT → 全格式恢复 → 释放 mutex`。
三个容易漏的点：
1. 只备份"纯文本"是不够的，用户剪贴板里常常是图片/文件/HTML，必须**逐 format**备份（`OleDuplicateData`）；
2. 恢复要在 **`finally`** 里做，并且**中途被打断也要恢复**（夸克用"鼠标时间变了"当打断信号）；
3. 剪贴板被别的进程占用时 `OpenClipboard` 会失败 → 要**有限次重试 + 超时**（`max_try`）。

### 痛点 C：「VSCode 取不到」
👉 两条腿都补上：
1. **补 MSAA**（不是 UIA）：`AccessibleObjectFromWindow(hwnd, OBJID_CLIENT, IID_IAccessible)` →
   `get_accSelection()` → 对每个 `IAccessible` 取 `get_accValue(VAR_CHILDID_SELF)`；
   失败再试 `OBJID_CARET` + `IAccessibleText::get_text`。
   Electron/Chromium 系（VSCode）在你挂上客户端后会按需开 AX，不要求用户手动开"屏幕阅读器支持"。
2. **兜底快捷键换成 `Ctrl+Insert`**（比 `Ctrl+C` 命中面更广：记事本/Office/浏览器/VSCode 都认，
   而且不容易被应用自定义键位吃掉）。取不到就**安静地什么都不弹**，不要弹空工具条。

### 推荐架构（any-menu）

```
[独立的小 helper（推荐）]
   ├─ WH_MOUSE_LL 钩子（或 50ms 轮询 GetAsyncKeyState(VK_LBUTTON)）
   ├─ 状态机: DOWN(记录 pt/time/hwnd/proc) → MOVE(位移阈值) → UP
   ├─ 过滤: 进程名白名单(本地配置) / 排除自身进程 / 排除本应用窗口
   ├─ 取文本: MSAA → (表格:COM) → Ctrl+Insert+剪贴板(全格式备份恢复)
   └─ 非空 → 弹窗（WS_EX_NOACTIVATE + WS_EX_TOOLWINDOW + SW_SHOWNOACTIVATE）

[Electron 侧]
   BrowserWindow({ frame:false, transparent:true, alwaysOnTop:true,
                   skipTaskbar:true, focusable:false, show:false })
   win.showInactive()      // ★ 千万别用 show()
```

要点：**helper 单独进程**更稳（钩子回调必须在有消息循环的线程里，且 Electron 主进程被 JS 阻塞时
钩子会拖慢全局鼠标——`WH_MOUSE_LL` 是**同步**的，回调里千万别做重活，只记录状态 + `PostMessage`）。

判定建议（比夸克更好做的部分，因为你可以给用户开配置）：
- 白名单默认给一批（`Code.exe`/`notepad++.exe`/`WINWORD.EXE`/`chrome.exe`/`msedge.exe`/`QQ.exe`/`WeChat.exe`…），
  并且**允许用户自己加**（夸克只能等服务端下发，这点你可以做得更好）；
- 额外加 `win_class` 黑名单（排除 `Shell_TrayWnd`/`Progman`/`WorkerW` 等），比单纯进程名更稳；
- `text_cursor`（`GetCursorInfo().hCursor == LoadCursor(NULL, IDC_IBEAM)`）作为"要不要试一下"的廉价预判，
  但**不要**把它当硬门槛（很多自绘编辑器永远是箭头）。
