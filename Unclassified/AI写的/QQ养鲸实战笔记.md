# 在 QQ 里养一只鲸：DeepSeek Harness 实战笔记

> 两天，从零搭出一个会聊天、会撒娇、会画画、会认图的群友。
> 不是产品介绍，是踩坑记录 + 可复制的做法。

---

## 0. 写在前面

起因很简单：群里缺个活人。不是那种"关键词触发 + 固定话术"的机器人，而是能看上下文、能接梗、被叫到会应一声、还能随手画两张图的那种。

选 DeepSeek Harness（下称 DSH）是因为它天生适合干这个：桌面端常驻、有插件体系、有 MCP 工具层、而且模型和工具是分开的——工具能自己写。

两天下来她现在的状态：

| 能力 | 实现方式 | 状态 |
| --- | --- | --- |
| 群聊/私聊对话 | SnowLuma + qq-bridge + DSH 会话 | ✅ 稳定 |
| 人设（鲸鱼娘「小柒」，撒娇、叫「哥哥」） | 角色卡注入 | ✅ |
| 主动找人说话、潜水、被叫醒 | reserved2 会话状态机 | ✅ |
| 发表情包 | 本地大目录直发 + QQ 收藏表情 | ✅ |
| 画画 | 本地 ComfyUI（SD1.5 + LoRA） | ✅ |
| 画特定角色（原神等） | 角色 LoRA 叠加 | ✅ |
| 图生图（把手绘图转风格） | ComfyUI img2img | ✅ |
| 认图 / 画猜 | 本地 WD14 打标 + 模型视觉 + 检索 | ✅ 可用，新角色需兜底 |
| 群静音开关 | 桥接白名单热更新 | ✅ |

写这篇的目的：网上关于"把 LLM 装进 QQ 群"的内容要么停在"接入成功"，要么全是产品文档口吻。真正难的是**接进去之后**——它说话像客服、它画画翻车、它认不出新角色、它一重启就断线。这篇主要写这些。

阅读方式：可以顺着读，也可以挑章节直接抄配置。第 10 章是运维手册，出问题直接翻那。

---

## 1. 全景：四层架构与一条消息的旅程

整套东西由四层组成，每层都能单独换掉——这是后面能持续折腾的前提。

| 层 | 角色 | 具体是谁 |
| --- | --- | --- |
| 决策层 | 想说什么、要不要调工具 | DSH + 模型 |
| 翻译层 | 把 QQ 消息变成会话上下文，把回复变成 QQ 消息；管会话状态 | qq-bridge（独立进程） |
| 通道层 | 接 QQ NT，暴露 OneBot 协议 | SnowLuma |
| 工具层 | 画画、识图、发表情、读写文件 | 自己写的 MCP 服务（qq-tools） |

一条群消息的旅程大致是这样：

1. 群友发言 → SnowLuma 通过注入 QQ 进程的 hook 拿到消息，转成 OneBot 事件
2. 事件经 WebSocket 进 qq-bridge，桥接判断：这个群在不在白名单、要不要叫醒她（潜水/活跃、@、关键词、概率）
3. 该回的话，桥接把上下文打包成一次会话请求发给 DSH，模型开始思考
4. 思考过程中如果要画画/发表情，模型调用 MCP 工具，工具直接操作 ComfyUI 或 OneBot
5. 回复文本回到桥接，桥接按"真人节奏"发出去（分条、随机间隔）

**为什么这么分层**：决策层换成别的模型不影响下面；通道层换成别的网关不影响上面；工具层可以随时加新能力。这两天里我换过模型、换过画图引擎、换过打标器，每一次都只动一层。

## 2. Day 1 上午：先把通路打通

### 认知纠正：桥接不是插件

一开始我以为 `github.com/Derpyu520/qq-bridge` 是个 DSH 插件，`dsh plugin add` 就能装。实际上它是个**独立进程**（`private: true`，压根不打算发到插件市场），通过 DSH 的 HTTP/WS 远程接口和桌面端通信。

所以正确的姿势是：把它当一个小服务跑，配置它连到本机的 DSH，再让它连到本机的 QQ 网关。三者是并列关系，不是父子。

### SnowLuma 的三个硬要求

1. **必须管理员运行**。它靠注入 DLL 到 QQ NT 进程来收发消息，普通权限注入不进去。表现是"启动成功但检测不到 QQ 主进程"。
2. **必须先有 QQ 在跑**。hook 是打到已存在的进程上的。
3. **工作目录要对**。我第一次用管理员 bat 启动，结果它把工作目录当成了 `C:\Windows\System32`，找不到自己的文件。

三个坑踩完，通道就通了：OneBot HTTP 3000、WS 3001、WebUI 5099。

### 两个必须记住的细节

**token 是自动发现的，而且两个不一样。** 桥接会从网关的配置文件里读 accessToken，HTTP 和 WS 的 token 是分开的。手动填错就会一直 401。

**端口冲突很常见。** SnowLuma 发现 5099 被占会自动改用 5100。看起来"起来了"，实际是两个实例在抢。判断方法很简单，看进程数：

```powershell
netstat -ano | findstr ":5099 :3000"
```

同一个 PID 占着 3000 和 5099 才是正常的一个实例。

### 最阴的一个坑：hook 会静默失效

QQ 重启（或者重新登录）之后，SnowLuma 还活着、端口还在、WebUI 还能开——但**一个事件都收不到**。

桥接的日志这时候特别有用，它会自己诊断出来：

> SnowLuma 上游不健康：已连接但 10 分钟没有收到任何事件包（连 30 秒一次的心跳都没有）……这不是桥接的问题。

修复很土：**每次 QQ 重启，回 SnowLuma 的注入页手动重新 hook**。这条后来被我写进了自己的运维清单。

## 3. Day 1 下午：给它一个「人」

### 角色卡怎么写

技术上是把一个 Markdown 文件注入到每次对话的开头。真正花时间的是内容设计。我的结构是：

1. 身份（你是什么、叫什么）
2. 语气规则（怎么说话、口头禅、句长）
3. 群聊铁律（什么时候别说话、别做什么）
4. 边界（不碰什么话题）
5. AI 味黑名单（明确禁止"作为 AI 助手""希望可以帮到你"这类句式）
6. 回复示例（正例反例各一两条）

第 6 条最有效。模型对"示例"的服从度远高于对"规则"的服从度。

### 一次改设定的复盘

第一版是"傲娇助手"，效果是——她确实会怼人，但对所有人都一个态度，群里显得很吵。

改成"软萌撒娇"之后好了很多，关键改动不是形容词，而是**加了三条行为约束**：

- 被叫到才说话，不主动刷存在感
- 一次只说一到两句，不写小作文
- 对 owner 用敬称（"哥哥"），对其他人正常称呼

**结论：人设靠的是行为约束，不是形容词堆叠。**

### 6000 字符的天花板

角色卡有注入字数上限（默认 6000）。这个限制在加的规则越来越多时会很疼——我最后一次加"识图兜底"规则时，全文已经 4478 字符，离上限不远了。

应对办法：把可复用的部分挪出去（工具说明写进工具的 description，让模型按需看到，而不是常驻在角色卡里）。

## 4. 群聊不是聊天：会话状态机

这块是"像不像活人"的分水岭。

### 潜水与活跃

她有两种状态：

- **潜水（diving）**：不主动说话，只有满足唤醒条件才醒
- **活跃（active）**：每条消息都看

唤醒条件是组合的：被 @、被叫名字、命中关键词、被提问、被拍一拍、指定群友发言、普通消息按概率唤醒。

默认给了她"潜水 + 小概率唤醒"，效果是群里聊十句她插一句，频率刚好。

### 沉睡前的那 5 分钟观察

设计上有个很细的点：她想睡觉之前，必须先在 5 分钟窗口里确认没人说话，才能进入潜水。否则会出现"刚睡着就被叫醒、又被叫醒"的抖动。

这条规则写在工具描述里，模型会自己遵守——**用工具描述约束行为，比在角色卡里写"你要先观察"更可靠**。

### 频率上限

默认限制是每分钟最多唤醒 1 次、每小时 12 次。听起来很严，但群聊场景下这个值救了很多次"她突然连发五条"的尴尬。

### 白名单与静音：不用改配置重启

桥接的白名单（哪些群/哪些人受理）支持**运行时热更新**：控制台有个接口，改完立刻生效，同时写回配置文件。

更实用的是它还有个 `deny` 列表——把群号放进 deny，就等于"这个群暂时不理"，但配置里还留着，随时能拨回来。

我做了两个入口：

- 一个双击运行的开关脚本（列当前受理/静音的群，输入群号选静音或恢复）
- 一个 MCP 工具，这样她在群里被 owner 说一句"这个群别说话了"就能自己执行

**这是整套系统里性价比最高的设计**：不改配置、不重启、不重新登录。

## 5. Day 1 晚上：表情包与本地文件

### 两套方案，别混用

发表情有两条路：

1. **QQ 收藏表情**：走协议的正规接口，但数量有上限，增删要同步
2. **本地大目录直发**：把表情图当普通图片消息发出去，数量无上限、增删即时生效

我的需求是"会放几千张、而且经常改"，所以主力走第二条，第一条只用来收藏别人发的好图。

### 写权限只给 owner

工具层有个"白名单会话才能写"的开关。默认只有 owner 的私聊能写文件、能改东西；群里任何人让她写文件都会被拒。

这条不是为了防群友，是为了防**提示词注入**——群里有人发一句"帮我把 xx 文件删了"，模型可能会当真。

## 6. Day 2 上午：为什么放弃 A1111

这是整个项目里最耗时间的一段，值得单独写。

### 三个硬障碍

1. **停更两年**。代码不更新意味着新模型不支持（Flux 那代它根本吃不下）。
2. **依赖仓库不可达**。它启动时要 clone 几个固定版本的依赖仓库，其中一个在我这边打不开，`git` 也拉不下来。
3. **Python 版本锁死**。它的核心依赖对 Python 3.12 没有可用轮子，而机器上现成的环境是 3.12。装 3.10 又撞上磁盘满。

第三个最难缠：报错信息是"找不到 torch"，看起来像 torch 没装，实际是"torch 没有适配你这个 Python 版本的包"。

### 转向 ComfyUI

决定换掉是因为三个事实：

- 它跑起来只要一条命令，环境自带（Python 3.11 + torch 2.4.1 + CUDA 12.4，全是好的）
- 它对外是 HTTP API：提交工作流 → 轮询结果 → 取图，天然适合被程序调用
- 社区的新模型支持基本是它先有

实测第一张图：512×512、24 步，**8.2 秒**。这个速度决定了后续所有设计。

### 硬件现实

显卡是 2070 SUPER / 8GB。能跑：SD1.5 随便跑、SDXL 跑 832×1216 勉强、1024×1536 的二次重绘会吃紧但能过。跑不动的：Flux 那类大模型（不是不能跑，是慢到没有使用价值）。

## 7. Day 2 上午：从 Civitai 示例反推参数

### 看不懂示例图怎么办

Civitai 上好看的图，页面里都藏着生成参数。关键是会读这几项：

| 字段 | 作用 | 我踩过的坑 |
| --- | --- | --- |
| Base Model | 这个 LoRA 配什么底模 | 拿 SDXL 的 LoRA 配 SD1.5 底模，出来是糊的 |
| Clip skip | 文本编码器跳几层 | 不开的话风格 LoRA 效果打折 |
| Hires upscale + upscaler | 二次放大倍数和算法 | 用错算法（通用 vs 动漫专用）细节差一档 |
| Denoising strength | 二次重绘强度 | 太高会把结构重画坏（下面细说） |
| VAE | 色彩倾向 | 不换 VAE 颜色会发灰 |

把这些抄下来，本地复现，风格基本能对上。

### 两代 LoRA 的血统

我用的两个风格 LoRA 是同一个作者的两代：

- **新手草稿**：纯铅笔灰阶，像速写本上的稿子
- **新手涂鸦**：小学生蜡笔/马克笔那种，彩色、线条粗

它们**不能混用**：草稿那套的提示词里带 `greyscale, monochrome`，套到涂鸦 LoRA 上会把颜色全压掉——这是我最开始复刻失败的直接原因，白折腾半天。

### 四档预设

最后固化成四档，靠一句话切换：

| 预设 | 底模 + LoRA | 风格 | 耗时 |
| --- | --- | --- | --- |
| 草稿（默认） | 原味 SD1.5 + 草稿 LoRA | 铅笔灰阶 | ~60s |
| 灰调 | 另一个 SD1.5 底模 + 草稿 LoRA | 灰调更柔、体积感更润 | ~60s |
| 涂鸦 | 原味 SD1.5 + 涂鸦 LoRA | 蜡笔彩色涂鸦 | ~60s |
| 彩色 | 动漫 SD1.5 底模，不挂风格 LoRA | 精致彩色插画 | ~65s |

默认给草稿，因为"速写本感"最不像 AI 画的。

### 角色 LoRA 叠加

风格 LoRA 之后再串一个角色 LoRA，就能"用草稿风画某个角色"。实测原神角色（纳西妲、芙宁娜、荧、雷电将军、妮露、诺艾尔、安柏、丽莎、八重神子）还原度都够。

有个细节：角色 tag 里的括号要转义，否则会被当成"加权语法"处理，出来不是那个角色。

## 8. Day 2 下午：翻车与修复

这一节全是失败的记录，但我觉得比成功的有用。

### 翻车一：三只手

单张 512×768 出图时，手部结构经常崩——多一只手、手指粘连。

修法不是加分辨率，而是**加负向权重**：把"多手/多指/畸形肢体"这些词带权重压下去。有效，但不彻底。

### 翻车二：画面变成"参考图排版"

有几次出来的是"一个人物 + 旁边两个头像特写"的排版，因为模型把"草图/速写本"理解成了"设定集"。

修法是负向加"多视角、参考图、分镜、拼图"这类词。加完之后干净了很多。

### 翻车三：铅笔风被二次重绘毁掉

这是最反直觉的一条。

想提高细节，第一反应是"放大 + 再重绘一遍"。结果：

- 铅笔草图经过二次重绘，**要么变成扁平的黑色线稿，要么变成数码绘画**——铅笔的颗粒感和排线全没了
- 二次重绘的强度设到 0.6 时，手和腿的结构会崩得更厉害

最后的结论：**铅笔风不走二次放大**，直接单遍出图（尺寸调大一点），宁可不放大也不能毁风格。彩色插画才走放大。

### 翻车四：想"更精细"反而更差

有段时间我把默认画质调成最高，结果用户反馈"时间长了反而效果更差"。

原因就是上面那条：重绘强度太高。把二次重绘的强度从 0.6 降到 0.45、步数从 20 提到 24，质量才稳住。

**教训：质量和时间不是单调关系，中间有个峰值。**

### 一次只能画一张

并发提交两张图会把显存和队列拖崩。所以加了个"画图锁"：正在画的时候，新请求直接拒绝，返回一句"正在画上一张（已 N 秒），画完再叫我"。

模型收到这个返回，会主动跟对方说"我在画啦，等我一分钟"。**把拒绝理由做成模型能读懂的字段，比报错更有用。**

## 9. Day 2 下午：让它会认图

### 多模态的边界

模型确实能"看见"图片（图片会被转成多模态输入），但**看见 ≠ 认得出**。

它对"一栋房子、一只猫"没问题，对"这是原神里的哪个角色"基本靠猜——普通视觉模型没有角色知识库。

### 本地打标器：1 秒出标签

ComfyUI 生态里有个 WD14 打标节点（danbooru 标签分类器）。跑一张图，1 秒内返回几十个标签：

```
nahida_(genshin_impact), 1girl, solo, long_hair, green_eyes,
white_hair, hair_ornament, white_dress, pointy_ears, ...
```

角色名、发色、瞳色、服饰、构图全有。对动漫角色这块，比通用视觉模型准得多，而且免费、不出网。

### 词表过期：为什么认不出新角色

问题在于**打标器的知识是被"训练时烧进词汇表"的**。

我查了手头那个模型的标签表（10,862 个标签）：

- 纳西妲、芙宁娜、克洛琳德 —— 在
- 卡其娜、玛薇卡、希诺宁、茜特菈莉 —— **全都没有**

也就是说它的知识停在 2024 年中。纳塔版本之后的角色一律不认识。

### 换新词表

找到了一个 2026 年更新的社区打标器，词汇表 **16,473 个标签**，验证过包含纳塔角色、以及鸣潮的角色。

坑在于：它只提供 safetensors 权重，而 ComfyUI 的打标节点只认 ONNX。于是得自己转：

1. 下载权重（约 1.2GB）
2. 用模型架构对应的开源视觉模型骨架重建网络
3. 导出 ONNX，输入固定 448×448，输出维度要和标签表条数对齐
4. 把 ONNX 和标签表一起放进打标节点目录

转换本身不难，难在依赖：目标环境的 Python 里缺 ONNX 相关包，而且它的嵌入式 Python 会忽略 `PYTHONPATH`，只能手动把库路径插进 `sys.path`。前后试了四轮才对。

**这件事最值得记的一点**：本地模型的"知识更新"是有成本的（下载 + 转换 + 拷贝），但它是一次性的；在线 API 是每次付费换取"稍微新一点的知识"，而且下次更新又得重新付费。

### 三层组合方案

最后的识图方案是三层叠加：

1. **标签层**（本地打标器）：给出硬事实——角色名、发色、服饰、构图
2. **眼睛层**（模型自己的视觉）：读图里的文字、看整体感觉、理解抽象涂鸦
3. **检索层**（联网搜索）：标签里没有角色时，用特征去搜"这是什么角色"

配套的行为规则也写进了角色卡：

- 标签里有角色名就直接用，别猜反
- 标签只是参考，图里的字、梗、夸张画法要自己看
- 手绘草图标签会很弱（打标器是按精美插图训的），以自己观察为主
- 认不出来就说认不出来，别硬编

## 10. 运维手册

### 服务自检

一条命令看关键端口是否都在：

```powershell
netstat -ano | findstr ":3000 :3001 :5099 :8188"
```

正常状态：3000/3001/5099 同一个 PID（QQ 网关），8188 一个 PID（本地出图服务），另有桥接自己的控制台端口。

### 常见故障对照表

| 症状 | 真实原因 | 处理 |
| --- | --- | --- |
| 端口在监听，但机器人完全不响应 | QQ 重启后 hook 失效，网关在"空转" | 回网关注入页重新 hook |
| 网关启动提示端口被占（5099 → 5100） | 已经有一个实例在跑 | 杀干净再启动一个 |
| 出图报"端口已被占用" | 本地出图服务已经在别处跑着了 | 不要重复启动，直接用现成的 |
| 配置文件改不动（拒绝访问） | 文件被程序占着 / 权限问题 | 停掉服务再改，或用别的编辑器 |
| 脚本/配置出现乱码或 JSON 解析失败 | 编码问题（BOM / ANSI 被当 UTF-8） | 统一存成无 BOM 的 UTF-8 |
| 打标器报"连不上 huggingface" | 首次使用要下载模型，而网络不通 | 手动下载模型文件放进节点目录 |

### 清端口的命令

```powershell
Get-NetTCPConnection -LocalPort 8188 -State Listen -ErrorAction SilentlyContinue |
  ForEach-Object { Stop-Process -Id $_.OwningProcess -Force }
```

先查 PID、确认路径再杀，别闭眼杀。

## 11. 成本与性能实测

| 项目 | 数据 |
| --- | --- |
| 单张图（快速档，512×768） | 约 8–12 秒 |
| 单张图（标准档，含二次放大） | 约 60–70 秒 |
| 识图打标 | 约 1 秒 |
| 对话响应（含模型思考） | 数秒到十几秒，取决于上下文长度 |
| 磁盘占用（模型） | 底模 2–7GB/个，LoRA 几十到几百 MB |
| 调用费用 | 出图、识图**全本地，零成本**；只有对话走 API |

**本地 vs 在线怎么选**：

- 高频（出图、识图）→ 本地。免费、无网络依赖、没有内容审查干扰
- 需要最新知识（认新角色）→ 本地做不到，靠检索补
- 需要读图里的小字 → 在线视觉模型更强（但这一环我最后没接，因为用得少）

## 12. 复盘

### 做对的三个决策

1. **桥接和大脑分开**。QQ 协议那层再乱，也不影响模型侧；模型换版本，也不用动协议。
2. **能力做成工具，不做成提示词**。画画、识图、发表情都是工具调用，不靠模型"记住怎么画"。工具描述里写清楚什么时候用、怎么用，比角色卡里写规则可靠。
3. **把运维入口做成聊天指令**。静音群、查 LoRA 这类操作，最后都做成了模型能调的工具——你不用开电脑，在群里说一句就行。

### 还没解决的

- **新角色画不出来**。打标器换新词表能认出来，但画图底模本身不认识这些角色，想要画得像必须配角色 LoRA。
- **角色卡逼近上限**。规则越加越多，6000 字符快满了，以后要么精简，要么把规则挪进工具描述。
- **图里的文字**。试过系统自带 OCR，但在我这边的执行环境里被权限挡住（WinRT 不允许沙盒进程读任意路径）。要么在网关进程里做，要么装独立的 OCR 组件，暂时搁置。

### 一句总结

两天的最大收获不是"接进去了"，而是搞清楚了**哪些能力该放在模型里，哪些必须放在模型外**。

画画、识图、发表情——这些放模型里怎么调提示词都不稳，做成工具之后立刻好用；而什么时候画、画什么、跟谁撒娇——这些留在模型里，反而灵。
